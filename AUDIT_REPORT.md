# Аудит и оптимизация STTEC Schedule

## Краткий итог
Проект в целом построен корректно: разделение на Core/DB/Bot/Web сохранено, асинхронные операции используются последовательно, код читаем и пригоден для поддержки. Ниже — перечень доработок, которые выполнены для повышения стабильности и экономии ресурсов, а также рекомендации под сервер с 8GB RAM.

## Что оптимизировано в коде

### Core (core.py)
- Добавлена карта быстрого поиска групп (нормализованные названия → ключ группы), чтобы избежать линейного поиска по списку при каждом запросе.
- Кэш замен теперь индексируется по нормализованному названию группы — это устраняет повторную нормализацию и перебор.
- Введён единый HTTP-клиент и блокировка для запросов замен, чтобы не плодить соединения и исключить гонки кэша.

### Database (database.py)
- Для SQLite используется `NullPool`, что снижает накладные расходы и корректнее для одиночного файла БД.
- Массовые операции (сброс флага болезни, удаление домашних заданий) переведены на SQL `UPDATE/DELETE`, чтобы не загружать сущности в память.

### Bot (bot_main.py)
- Добавлено создание каталога `logs`, чтобы файловый логгер не падал на пустой системе.
- В `job_smart_poll` расписание для группы вычисляется один раз на группу, а не на каждого пользователя.
- Добавлено закрытие HTTP-клиента core при выключении бота.

### Web (web_main.py)
- Добавлено создание каталога `logs`.
- Используется общий HTTP-клиент для отправки сообщений вместо создания клиента на каждый запрос.
- Закрываются ресурсы Core и HTTP-клиент при shutdown.

## Рекомендации для сервера с 8GB RAM

### Производительность
- **Uvicorn**: запускать 1–2 воркера (`--workers 1` или `2`) — избыточное количество не даст преимущества из-за SQLite и может увеличить память.
- **SQLite**: использовать один процесс, где возможно, либо вынести БД в отдельный сервис (PostgreSQL) при росте нагрузки.
- **Telegram Bot**: при высоких рассылках держать паузу (`sleep`) 50–100 мс между отправками, как сделано сейчас.

### Надёжность
- Включить ротацию логов (logrotate), иначе файлы логов будут расти бесконечно.
- Убедиться, что `REPLACEMENT_URL` отвечает быстро; при нестабильной сети увеличить таймаут до 15–20 секунд.

### Пользовательский опыт
- Для API желательно вернуть более детальные ошибки валидации (например, формат даты), но это уже относится к уровню UI/UX.

## Итог
Выполненные изменения уменьшают количество лишних соединений, ускоряют выборку групп и снижают нагрузку на память при массовых операциях. Проект готов для работы на сервере с 8GB RAM и может масштабироваться при необходимости (с переходом на Postgres и лог-ротацией).
